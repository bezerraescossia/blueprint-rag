# Blueprint-RAG Constitution

## Core Principles

### I. LangChain as the Orchestration Framework, Used Plainly
LangChain MUST be the mandatory orchestration framework for retrieval, prompting, and chain composition. Custom abstraction layers, wrappers, or DSLs on top of LangChain's primitives MUST NOT be introduced — use its interfaces directly. Rationale: as a *starter template* meant to be forked and adapted, extra layers of indirection make the codebase harder to read and customize; YAGNI applies even here.

### II. Reproducibility by Default
Every pipeline run MUST be reproducible: environments MUST be pinned (lockfiles or containers), random seeds MUST be fixed and recorded, and all datasets/embeddings used to build or evaluate the index MUST be versioned with DVC. Rationale: RAG quality depends on data and embedding state as much as code; without versioning, "it worked yesterday" bugs become unresolvable.

### III. Mandatory Evaluation Gate
No change to the retrieval or generation pipeline may ship without passing evaluation against a held-out eval set, reporting retrieval metrics (recall@k, MRR) and generation metrics (faithfulness, answer relevance). Rationale: RAG systems can regress silently (e.g., a prompt tweak that improves fluency but hurts groundedness); a gate makes regressions visible before release.

### IV. Abstain Over Hallucinate
When retrieval confidence is low or no supporting context is found, the system MUST fall back to an explicit "I don't know" / abstention response rather than generating an unsupported answer. Rationale: for a generic template that will be adapted to unknown downstream domains, silently confident wrong answers are a worse failure mode than an honest refusal.

### V. Observability from Day One
Structured logging and tracing MUST be present from the first working pipeline, capturing at minimum: retrieved document IDs, retrieval/generation latency, and token usage per request. Rationale: debugging RAG relevance and cost issues without this data is impractical, and retrofitting observability later is disproportionately expensive.

## Data Governance

No PII or regulatory compliance controls (e.g., GDPR/HIPAA handling, access control, retention policies) are assumed by default. The template assumes documents are non-sensitive. Any adopter deploying against sensitive or regulated data MUST add their own compliance layer on top of this template — it is explicitly out of scope here.

## Development Workflow

Any change to the retrieval or generation pipeline MUST pass the Evaluation Gate (Principle III) before merge. Spec, plan, and task artifacts generated by the SDD pipeline (`sdd-specify`, `sdd-plan`, `sdd-tasks`) MUST be checked against these principles; a plan or task that violates a principle MUST either be revised or the violation explicitly justified and recorded.

## Governance

This constitution supersedes any ad-hoc convention when the two conflict. Amendments require:
1. A documented rationale for the change (what evidence or decision prompted it).
2. A semantic version bump: MAJOR for removal/redefinition of a principle, MINOR for a new principle/section or material expansion, PATCH for clarifications or wording fixes.
3. Updating `Last Amended` below (keeping `Ratified` unchanged) and prepending a Sync Impact Report as an HTML comment.

All future specs, plans, and task lists for this repository MUST be reviewed for compliance with this document before implementation begins.
